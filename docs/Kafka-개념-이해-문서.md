# Kafka 개념 이해 문서

> Kafka를 처음 접할 때 헷갈리기 쉬운 개념들을 "오해 → 정답" 구조로 정리한다.
> 각 절은 실제로 혼동하기 쉬운 질문에서 출발한다. 설정·설계 근거는 [Kafka 설계 문서](./Kafka-설계-문서.md) 참고.

---

## 0. 전체 그림 — 회사 비유 하나로 시작

```
회사에 실시간으로 들어오는 "주문 접수 문서함"  = 토픽
문서함 안의 기록장 3권 (읽어도 안 지워짐)      = 파티션
기록장을 읽는 일꾼 (앱 안의 스레드)            = 컨슈머
일꾼들의 팀 (그룹 ID로 묶임)                  = 컨슈머 그룹
```

- 물류팀이 문서를 읽고 배송한다 → **소비**
- 물류팀에 사람을 충원해 기록장을 나눠 읽는다 → **스케일링**
- 재무팀을 신설해 같은 문서함을 처음부터 또 읽는다 → **fan-out (멀티 컨슘)**

이 문서 전체가 이 비유 위에서 돈다.

---

## 1. 토픽 vs 파티션 — 종류를 나누는 건 토픽, 파티션은 차선

**오해**: "파티션 3개 = 로그 파티션, 메트릭 파티션, 트레이스 파티션처럼 종류별로 나뉜 것"

**정답**: 데이터 **종류**를 나누는 건 **토픽**이고, 파티션은 **같은 종류의 데이터를 병렬 처리를 위해 3등분한 것**이다. 파티션 0이든 2든 내용물의 성격 차이가 전혀 없다.

```
Kafka
├── 토픽 traces          ← 트레이스만 (종류 구분은 여기서)
│   ├── 파티션 0 ─ 트레이스 일부
│   ├── 파티션 1 ─ 트레이스 일부
│   └── 파티션 2 ─ 트레이스 일부
└── 토픽 metrics         ← 메트릭만
```

도로 비유: **토픽 = 도로** (트레이스 도로, 메트릭 도로 — 목적지가 다른 별개의 길),
**파티션 = 그 도로의 1·2·3차선** (같은 곳으로 가는 같은 종류의 차량, 차선을 나눈 이유는 오직 동시에 더 많이 지나가게 하기 위함).

한 줄 원칙: **종류 격리는 토픽으로, 병렬화는 파티션으로.**

같은 발신자(Collector)가 여러 토픽에 쓰는 것도 자연스럽다 — 우편실이 들어온 우편물을 종류별 문서함에 분류해 꽂는 것뿐이다. 메시지 하나는 정확히 한 토픽에만 들어간다.

---

## 2. 파티션은 큐가 아니라 로그 — 읽어도 안 지워진다

**오해**: "파티션 = 데이터를 적재하는 큐"

**정답**: 큐는 꺼내면 사라지지만, 파티션은 **읽어도 데이터가 남는 추가 전용(append-only) 로그**다. 컨슈머는 데이터를 "가져가는" 게 아니라, 각자 책갈피(오프셋)를 들고 "읽어가는" 것이다.

이 한 가지 성질에서 Kafka의 대표 능력이 전부 파생된다:

| 능력 | 왜 로그라서 가능한가 |
|------|---------------------|
| fan-out (멀티 컨슘) | 읽어도 남으니 몇 팀이든 각자 다시 읽을 수 있다 |
| 재생(replay) | 오프셋을 되감으면 과거분부터 다시 읽는다 |
| 사후 팀 추가 | 나중에 만든 컨슈머도 `--from-beginning`으로 소급 가능 |

데이터가 지워지는 유일한 시점은 소비가 아니라 **retention 만료**다.

---

## 3. 파티션 배정 — 해시가 결정하고, 프로듀서가 계산한다

**오해**: "브로커가 받아서 적절히 분배한다"

**정답**: 어느 파티션에 갈지는 **프로듀서가 보내기 전에** 결정한다. 규칙은 세 가지:

1. **키가 있으면 해시**: `파티션 번호 = hash(키) % 파티션 수` — 같은 키는 항상 같은 파티션 (traces 토픽: 키 = trace_id)
2. **키가 없으면 라운드로빈 계열**: 배치 하나를 한 파티션에 채우고 다음 배치는 다음 파티션으로 (metrics 토픽)
3. 명시 지정 (특수 경우)

키 선택의 의미: **"무엇의 순서를 지킬 것인가"의 결정**이다. trace_id를 키로 쓰면 같은 트레이스의 span 5개가 전부 같은 파티션 = 같은 컨슈머에 도착한다.

## 4. 파티션은 많을수록 좋은가 — 아니다, "적정 사이즈" 문제다

**오해**: "차선이니까 많을수록 좋다"

**정답**: 부족하면 확장이 막히고 과하면 오버헤드다.

**많으면 좋은 것**: 병렬 처리 상한(=컨슈머 확장 천장)이 올라간다. 백로그 해소 능력이 커진다.

**많으면 나쁜 것**:
- 파티션 하나 = 디렉터리 + 세그먼트 파일 + 파일 핸들 + 인덱스 메모리 (브로커 자원)
- 브로커 장애 시 리더 재선출 대상이 많아져 복구가 느려진다
- 프로듀서 배치가 파티션별로 잘게 쪼개져 요청 수 증가·압축률 하락
- **키 파티셔닝은 파티션 수 변경이 사실상 불가** — `hash % N`의 N이 바뀌면 키→파티션 매핑이 통째로 바뀐다. 늘릴 수는 있지만 줄일 수는 없고, 늘리는 순간 같은 trace_id가 변경 전후로 다른 파티션에 걸친다

**운영의 실제 모습**:
```
파티션 수 = 설계 시점에 박는 상수 (예상 최대 컨슈머 수보다 약간 크게)
일상적인 조절 손잡이 = 컨슈머 수
```
밀린 백로그는 컨슈머 증설로만 따라잡을 수 있다 — 파티션을 나중에 늘려도 이미 쌓인 데이터는 재분산되지 않는다. (카카오페이증권: 파티션 150 고정, 컨슈머 15~50으로 조절)

apm-infra가 3개인 솔직한 근거: 처리량 기준이면 1개로 충분하다. 3개는 ① 키 파티셔닝이 눈에 보이게 (1개면 전부 파티션 0), ② 컨슈머 1→3 수평 확장 시연, ③ 로컬 단일 브로커에서 오버헤드 0 — 학습 시연 목적의 최소 복수 구성이다.

## 5. 컨슈머는 서버가 아니라 스레드다

**오해**: "컨슈머 = 서버(스프링 인스턴스)"

**정답**: 컨슈머는 그룹 ID를 갖고 토픽을 poll하는 **클라이언트 스레드**이고, 서버는 그걸 담는 그릇이다. 계층:

```
컨슈머 그룹                          ← 논리적 팀 (그룹 ID)
 └── 인스턴스(프로세스/서버) 1~N대   ← 물리적 배치
      └── 컨슈머 스레드 1~M개        ← 파티션 배정의 실제 단위
```

Kafka는 그룹 안의 스레드 총합(N×M)만 본다. 파티션 3개 기준으로 아래 세 구성은 처리량이 같다:

- 서버 1대 × 스레드 3 (`@KafkaListener(concurrency = "3")`)
- 서버 3대 × 스레드 1
- 서버 1대 × 스레드 5 → 2개는 유휴 (파티션보다 많으니)

서버를 여러 대 두는 이유는 처리량이 아니라 **한 대의 자원 한계 돌파 + 가용성**(한 대가 죽어도 리밸런싱으로 소비 지속)이다.

## 6. 스케일링 vs 멀티 컨슘 — 일꾼 충원 vs 팀 신설

**오해 1**: "멀티 컨슘 = 일꾼(스레드)을 많이 늘리는 것"
**오해 2**: "멀티 컨슘 = 토픽·파티션·컨슈머를 복제해서 쓰는 것"

**정답**: 구분 기준은 스레드 수가 아니라 **그룹 ID**다.

```java
// 스케일링 — 같은 그룹, 일꾼 충원. 메시지 하나는 딱 한 번 처리 (분업 → 속도)
@KafkaListener(topics = "traces", groupId = "clickhouse-writer", concurrency = "3")

// 멀티 컨슘 — 다른 그룹, 팀 신설. 같은 메시지가 팀 수만큼 처리 (fan-out → 용도)
@KafkaListener(topics = "traces", groupId = "alert-checker")
```

판별 질문 하나: **"메시지 한 개가 몇 번 처리되는가?"** — 1번이면 스케일링(더 빨리), N번이면 멀티 컨슘(다른 일도).

복제 오해에 대한 정답: 복제되는 건 **컨슈머 팀과 그 팀의 책갈피(오프셋)뿐**이고, 토픽·파티션(데이터)은 원본 한 벌을 공유한다. "도서관 책은 한 권, 독서 모임이 여러 개, 모임마다 자기 책갈피"가 정확한 그림이다. (RabbitMQ의 fanout은 발행 시점에 큐마다 메시지를 물리 복사하는, 진짜 복제 방식이다 — 8절)

멀티 컨슘의 진입 비용은 사실상 0이다 — 브로커에 팀 등록 절차가 없고, 처음 보는 그룹 ID로 접속하는 순간 성립한다. 유일한 결정은 시작점(`auto.offset.reset`: `earliest` 소급 / `latest` 지금부터). 다만 유지 비용은 실비다: 팀 수만큼 브로커 전송 부하가 늘고, 팀마다 lag 관리가 필요하다.

## 7. 분배 방식 — 스레드풀이 아니라 "담당 구역제 + pull"

**오해**: "한가해진 컨슈머가 다음 메시지를 집어가는 스레드풀 방식"

**정답**: 그 모델은 RabbitMQ다. Kafka는:

1. **소유권 고정**: 리밸런싱 시점에 "파티션 0 = 컨슈머 A 담당"이 정해지면 다음 리밸런싱까지 A만 읽는다. 빠른 컨슈머가 느린 컨슈머의 파티션을 대신 읽는 일(work stealing)은 없다
2. **pull**: 브로커는 배분하지 않는다. 각 컨슈머가 자기 담당 파티션에서 자기 속도대로 poll한다
3. **공정함은 생산 시점에 결정**: 부하 분배는 프로듀서의 파티셔너(키 해시/라운드로빈)가 이미 끝냈다. 키 분포가 나쁘면(핫 파티션) 소비 쪽에서 보정할 방법이 없다

이 설계의 대가로 얻는 것: 파티션 내 순서 보장, 단순한 오프셋 관리, pull 기반의 자연스러운 백프레셔(컨슈머가 처리 능력만큼만 가져감).

---

## 8. RabbitMQ와의 비교 — 갈림길은 "소비 후 데이터가 남느냐"

**오해 1**: "RabbitMQ는 파티션이 1개라서 멀티 컨슘이 안 된다"
**오해 2**: "RabbitMQ는 컨슈머를 못 늘린다"

**정답**: 멀티 컨슘 가능 여부를 가르는 건 파티션이 아니라 **큐(소비하면 삭제) vs 로그(소비해도 보존)** 다. 파티션 1개짜리 Kafka 토픽도 멀티 컨슘은 완벽하게 된다.

| | Kafka | RabbitMQ 클래식 |
|---|---|---|
| 소비 후 메시지 | 보존 (retention까지) | **삭제** |
| 분배 방식 | 담당 구역 고정 + pull | 한가한 컨슈머에 push (스레드풀식) |
| 컨슈머 증설 | ⭕ 단, 파티션 수가 천장 | ⭕ 천장 없음 — 오히려 더 유연 |
| 순서 있는 병렬 | ⭕ 파티션 | ❌ 컨슈머 2개부터 순서 소멸 (파티션 없음) |
| fan-out | 그룹 추가만 (무복사) | fanout exchange가 **큐마다 복사** + 사전 바인딩 필수 |
| 재생(replay) | ⭕ 오프셋 되감기 | ❌ 소비 즉시 삭제라 불가 |

역할 정리: **멀티 컨슘·재생의 열쇠 = 로그, 순서 있는 병렬의 열쇠 = 파티션.** RabbitMQ는 둘 다 없어서 각각 복사(fanout exchange)와 큐 쪼개기(hash exchange)로 우회한다. RabbitMQ는 "한 번 처리하고 끝나는 작업 큐"(주문 처리, 메일 발송)에 맞는 도구이고, 텔레메트리처럼 재생·사후 용도 추가가 필요한 스트림에는 로그 모델(Kafka)이 맞다.

## 9. 순서가 꼬이지 않는 이유 — 섞일 통로를 4군데에서 차단

**질문**: "어떤 동작 과정 때문에 파티션의 데이터가 꼬이지 않는가?"

| 단계 | 장치 | 차단하는 것 |
|------|------|------------|
| ① 배정 | 해시는 보내기 전에 확정 | 배정이 흔들릴 여지 |
| ② 쓰기 | 파티션당 리더 브로커 1개 — 모든 쓰기가 한 입구로 | 쓰기 경합으로 인한 순서 섞임 |
| ③ 저장 | append-only + 오프셋 (끝에만 추가, 불변) | 쌓인 뒤 섞이는 경로. 파티션끼리는 물리적으로 다른 파일이라 침범 불가 |
| ④ 읽기 | 그룹 내 파티션 배타 소유 + 오프셋 순 소비 | 두 컨슈머가 번갈아 읽으며 순서를 흩는 것 |

**경계선**: 이 보장은 **파티션 안**까지다. 파티션끼리는 순서 개념 자체가 없다 — 그래서 순서가 필요한 데이터는 같은 키로 같은 파티션에 묶는다(trace_id).

## 10. 뒤섞여 적재돼도 되는 이유 — id 1~100 시나리오

**질문**: "파티션별로 제각각 소비되면 DB에는 어떻게 순서대로 들어가는가?"

**정답**: 순서대로 안 들어간다. **뒤섞인 채 들어가고, 그래도 되게 만들어져 있다.**

```
① 생산: id 1~100을 순서대로 발행 → hash % 3으로 뿔뿔이 흩어짐
   파티션 0: [2, 3, 9, ...]  파티션 1: [1, 5, 7, ...]  파티션 2: [4, 6, 8, ...]
② 소비: 컨슈머 3개가 각자 속도대로 → DB 도착 순서: 1, 5, 2, 7, 11, 4, 6, 3, 9, ...
③ DB: 뒤죽박죽 그대로 INSERT됨 (아무도 안 막음 — 정상 동작)
④ 조회: SELECT ... ORDER BY id → 1, 2, 3, ..., 100 (누락·중복·섞임 없음)
```

성립 조건 두 가지:
1. **순서 정보가 데이터 몸에 붙어 있다** — span은 "몇 등으로 도착했나"가 아니라 trace_id·parent_span_id·start_time을 지니고 다닌다 (이벤트 시간 ≠ 도착 시간). 도착 순서가 무의미해진다
2. **각 데이터가 독립적이다** — id 7 처리에 id 6이 선행할 필요가 없다

트레이스 조회가 하는 일 = [OTel Log 읽기 문서](./OTel-Log-읽기-문서.md) 4절에서 손으로 한 재조립(Trace ID로 모으고 Parent ID로 트리 구성)을 쿼리가 수행하는 것이다.

반례: CDC(DB 변경 이벤트)처럼 이벤트를 순서대로 적용해야 상태가 맞는 데이터(잔액 +100 후 -50 ≠ -50 후 +100)는 이 방식이 안 통하고, 파티션 순서 보장이 정확성 그 자체가 된다. 텔레메트리는 불변 사실의 나열이라 순서 의존이 없다.

## 11. DB의 정렬은 두 층이다

**질문**: "DB가 정렬해서 저장하는가, 우리가 쿼리에서 sort하는가?"

**정답**: 둘 다 — 목적이 다르다.

| 층 | 누가 | 목적 |
|----|------|------|
| 저장 시 정렬 (ClickHouse MergeTree) | DB가 자동 | **성능** — 정렬돼 있으면 인덱스처럼 구간만 읽고(sparse index), 비슷한 값이 붙어 있어 압축률 급상승 |
| 조회 시 ORDER BY | 쿼리에 명시 | **정확성** — SQL 규칙상 ORDER BY 없는 결과 순서는 미정의 (병렬 읽기로 섞여 나올 수 있음) |

MergeTree는 INSERT 배치를 정렬 키 기준으로 정렬한 "파트"로 기록하고, 백그라운드 머지가 파트들을 병합하며 정렬을 유지한다. 조회의 ORDER BY는 이미 정렬된 조각을 병합만 하면 되므로 거의 공짜다.

참고로 DB마다 다르다: PostgreSQL 힙 테이블은 도착 순서로 쌓고 B-tree 인덱스와 쿼리 정렬에 의존, MySQL InnoDB는 PK 기준 물리 정렬(클러스터드), ClickHouse는 테이블 전체가 정렬 키 기준 저장.

## 12. append-only가 빠르게 하는 건 DB가 아니라 Kafka 자신이다

**오해**: "Kafka를 쓰면 DB 적재가 빨라진다"

**정답**: 세 문장으로 갈라진다.

1. **append-only는 "순차 쓰기는 빠르다"는 원리다** — 디스크는 탐색(seek)이 병목인데, 파일 끝에만 이어 붙이면 탐색이 없다. 일반 DB의 쓰기 1건(B-tree 탐색 + 인덱스 갱신 + 제약 검사)과 달리 Kafka는 바이트를 꼬리에 붙일 뿐이다 — **Kafka 자신의 수신이 빠른 이유**
2. **DB에는 간접 이득을 준다** — 버퍼가 있으니 컨슈머가 모아서(수천 건) bulk INSERT할 수 있고(ClickHouse는 "큰 배치를 드물게"가 최적), 유입 스파이크가 평탄화되어 DB는 일정한 속도로만 받는다. 즉 "DB가 좋아하는 모양으로 다듬어 준다"
3. **ClickHouse가 빠른 이유도 같은 원리다** — MergeTree는 기존 데이터 사이에 끼워 넣지 않고 새 파트를 통째로 쓴 뒤 나중에 병합한다(append + 후정리). 순차 쓰기라 초당 수백만 row를 받는다

```
Kafka      : append-only 로그     → 수신이 빠름
ClickHouse : 파트 append + 후정리 → 적재가 빠름
텔레메트리 : 불변 사실의 나열     → 수정이 없어 append-only와 완벽한 궁합
```

## 한 장 요약

| 개념 | 한 줄 정의 | 헷갈림 방지 |
|------|-----------|------------|
| 토픽 | 데이터 종류별 채널 | 종류 구분은 여기서. 파티션이 아님 |
| 파티션 | 토픽 안의 병렬 차선 (append-only 로그) | 큐 아님 — 읽어도 남음. 많을수록 좋은 것 아님 |
| 파티션 키 | "무엇의 순서를 지킬 것인가"의 결정 | 해시 계산은 프로듀서가 함 |
| 컨슈머 | 토픽을 poll하는 스레드 | 서버가 아님. 파티션 배정의 단위 |
| 컨슈머 그룹 | 일꾼들의 팀 (그룹 ID) | 조절 손잡이는 파티션이 아니라 컨슈머 수 |
| 스케일링 | 같은 그룹에 일꾼 충원 → 분업 | 메시지 1개 = 1번 처리 |
| 멀티 컨슘(fan-out) | 다른 그룹 ID의 팀 신설 → 용도 추가 | 메시지 1개 = 팀 수만큼 처리. 데이터는 한 벌, 책갈피만 추가 |
| 순서 보장 | 파티션 안에서만 | 파티션 간 순서는 없음 — 그래서 키로 묶음 |
| 최종 순서 | 조회 시점에 재조립 | 데이터가 타임스탬프를 지니므로 도착 순서 무관 |
